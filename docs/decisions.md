## 一、决策清单

### 分支模型

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| **D-01** | 服务器上的改动走**独立分支**，不在远程主分支上直接改 | 用户的实际工作方式：公司和家里往主分支推，服务器的改动需要隔离，避免互相污染。这也决定了后面 `D-09` 必须把拉取来源与推送目标分开 |

### 自动同步语义

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| **D-02** | **无冲突就自动更新，有冲突就仅提示**，等用户手动处理 | 用户原话。关键是"仅提示"这一半——遇到冲突不能在无人值守时自作主张 |
| **D-03** | 脏工作区**不 stash**，直接 `git merge` | **这条最容易被人改回去，请读完理由。** `git merge` 本身就能在脏工作区下工作：只要未提交改动与上游改动不落在同一文件，merge 正常完成且改动原样保留；只有撞到同一文件时 git 才拒绝——而那恰好就是"有冲突"的情形，本来就要停下。所以 stash 是多余的：它引入了"恢复 stash 失败"这个新风险，却换不来任何额外能力 |
| **D-04** | 冲突**预判**用 `git merge-tree --write-tree`（需 git ≥ 2.38） | 能在动工作区之前判断出会不会冲突，把"仅提示"提前到真正安全的位置 |
| **D-05** | 预判无冲突但实际产生冲突时，立即 `git merge --abort` **回滚** | 不留半完成的合并状态。这是 `D-02` 与 `D-04` 之间的兜底。**边界**：`merge --abort` 能还原的前提是工作区在合并期间未被外部改动；带未提交改动执行合并时，此前提需要 `RK-01` 的缓解手段来保障（见 `plan.md` §9） |
| **D-06** | 轮询间隔**默认 60 秒**，设置页可调、可整体关闭 | 用户明确"可以手动设置，默认 1 分钟"。选轮询而非 webhook 先落地，因为轮询不依赖任何外部配置 |

### 导入与清单

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| **D-07** | **点按钮触发导入**；选到含多个仓库的父目录时**列出子仓库供勾选** | 用户明确要求"改成点一个按钮触发导入，而不是每个项目自动添加"。自动扫描会在服务器上误纳管大量无关目录 |
| **D-08** | 清单**持久化在 Host 侧**，客户端只读展示 | 单一数据源。客户端另存一份会导致两边状态漂移 |

### 同步来源与推送目标（本组是修正后的最终形态）

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| **D-09** | **拉取来源与推送目标是两个独立引用**，各自配置、在面板上分栏显示 | **这条最容易被人改回"上游"，改回去会出真问题。** 见下方"撤回记录 R-01"。一句话：把两个方向绑到同一个引用上，一定会有一端错 |
| **D-10** | 同步来源默认 **`origin/HEAD`**（远程默认分支） | 换仓库时自动适配，不用逐个配。写死 `origin/main` 会在默认分支叫 `master` 的仓库上失效。**该引用不保证存在**：它由 `git clone` 写入，`git init` + `git remote add` 的仓库没有它，远程默认分支改名后也会失效。因此需在**导入项目时**与**每轮同步前**各解析一次（`git symbolic-ref refs/remotes/origin/HEAD`），缺失时用 `git remote set-head origin --auto` 尝试修复；仍失败则**如实报错**，不得当作「无新提交」（见 `plan.md` §6） |
| **D-11** | 推送目标固定 **`origin/<当前分支名>`** | 服务器分支 `server` 的改动应当推到 `origin/server`，绝不推到主分支 |
| **D-12** | 推送时远程无同名分支：**默认自动创建并推送**，但设置页提供开关可关闭 | 用户选了"直接自动创建并推送"。我提出并保留下来的折中：`git push` 在远程创建分支是**对外可见的写操作**，风险不在失败而在成功——分支名打错就会在远程留下垃圾分支。所以保留用户想要的行为（默认开），同时给出关闭能力。**命令不附带 `-u`**：本插件不设置也不使用 upstream（见 `R-01`），`git push <remote> <branch>` 即可创建远程分支，无需写入仓库 `.git/config` |

### 提交与推送交互

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| **D-13** | 提交为**全量提交**，但**提交前列出将要提交的文件清单** | 用户选了"无冲突的全量提交"。我额外指出风险：`git add -A` 会把**未跟踪的新文件**（新脚本、日志、`.env`）一并带进去；已被 `.gitignore` 覆盖的 git 本来就会跳过，真正的风险是无意产生又没被忽略规则盖住的文件。列清单几乎不增加操作成本，却能挡住大部分误提交 |
| **D-14** | 提交信息**不调用 agent 生成** | 用户明确"不需要，插件不要动用 agent" |
| **D-15** | **保留**把 git 操作暴露为对话工具；但插件**自己不主动调用 agent** | 用户澄清了 `D-14` 的口径：禁的是"插件主动发起 agent 请求"（本来也没打算做），而不是"把能力暴露给对话"。所以对话工具保留 |

### 范围边界

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| **D-16** | **项目分组第一期不做** | 用户原话"不知道是做什么的"。我解释后建议先不做：项目在十几个以内时平铺更快，等确实多到一屏放不下，再按父目录自动分组。第一期能少做一块界面，也不先做一个用不上的东西 |
| **D-17** | **只管本机**，不做跨机器管理 | 用户确认"插件只管自己插件所在的应用上的"。数据模型因此不需要"机器"维度 |
| **D-18** | 本期**不做通知**，但把每次同步结果做成**可订阅事件点** | 用户说"到时候可能会接入 tg bot"。现在把通知逻辑写死进插件不划算；做成事件后，将来外部消费者订阅即可，插件本身不用改 |
| **D-19** | 分期改为：**P1 纯 UI 原型**（可点击、无实际功能、用浮层提示代替）→ P2 自动同步 → P3 增强 | 用户提出"第一步先把 ui 界面做出来，可点击但无实际功能"。我判断这比原定的"P1 功能"更稳：先定下界面形状、在浏览器里看到点到，再填真实逻辑；否则功能都写完了才发现布局不合意，返工成本高得多 |

### 安全与实现形态

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| **D-20** | 安全边界：**不代管凭据、不自动推送、不做 `stash`/`checkout`/`reset`/`--force`、同仓库串行** | 每一条都对应一类"静默丢失用户代码"或"不可逆对外动作"的真实风险。凭据配置被明确界定为**用户手动完成的动作**，插件只报告"远程不可达" |
| **D-21** | 实现形态：写在工作区里的**独立 bundle 包目录**，用插件管理器以绝对路径安装进 profile；**不修改 profile 的 `package.json`**，不在 profile 目录跑包管理命令 | 直接改 profile 会在 DSH 升级时被冲掉。独立包目录是唯一能跨升级存活的形态 |

## 二、撤回与否定记录

这些是**曾经考虑过、但被明确否掉**的方案。列出来是为了避免后人重新走一遍：

### R-01 ⚠️ 撤回：「跟踪当前分支的上游 `@{upstream}`」

**这是本项目中最重要的一个修正。** 我最初推荐"跟踪当前分支的上游"，用户也选了，
但在推演分支工作流时发现它在两种常见配置下都会出问题：

| 服务器分支的配置 | 后果 |
| --- | --- |
| `server` 分支 track 了 `origin/server` | `@{upstream}` 是 `origin/server` 而**不是** `origin/main`，自动同步**永远拉不到公司的改动**。而且它会安静地什么都不做，用户很难发现 |
| `server` 分支的上游设成 `origin/main` | 按"上游"推送会把服务器改动**推到 main 上**。这是对外可见的错误推送 |

**结论：两端共用同一个引用是错的。** 由此产生 `D-09` / `D-10` / `D-11`。

> 特别提醒接手者：**"上游"这个词在本插件的设计里是被刻意回避的。** 如果你在代码里看到
> `@{upstream}` 或 `--set-upstream-to` 被用于决定同步行为，那是 bug。

### R-02 ❌ 否定：「先 stash，再 merge，再恢复 stash」

替换为 `D-03`（直接 merge）。理由：`git merge` 在脏工作区下本来就能工作，stash 换不来额外能力，
却新增了"恢复 stash 失败"的风险。

### R-03 ❌ 否定：用 `rebase` 代替 `merge`

服务器分支上有自己的提交，rebase 会重写这些提交的哈希。在一个会自动运行的后台流程里重写历史，
代价远高于收益。

### R-04 ❌ 否定：只更新引用、不合并工作区（"语义 A"）

早期候选方案：`fetch` 后只更新 `origin/main` 引用，面板提示"有新提交 N 个"，合并完全由用户手动做。
**零冲突风险**，但用户明确要的是"云端有新提交能够自己拉取"，语义 A 不满足这个诉求。
相关但未被完全否掉的部分：**真正遇到冲突时退化为仅提示**，正是这种保守姿态（见 `D-02`）。

### R-05 ❌ 否定：自动扫描目录并纳管

会在服务器上误纳管大量无关目录。替换为 `D-07` 的显式导入。

### R-06 ❌ 否定：按"上游"推送

见 R-01。替换为 `D-11`。

## 三、决策之间的关系

有三组决策是**成对**的，改动其中一个必须同步检查另一个：

| 组合 | 说明 |
| --- | --- |
| `D-02` + `D-03` | "无冲突就更新"之所以能在脏工作区上安全实现，正是因为 `merge` 的语义天然如此。如果改掉 `D-03`（比如改成先 stash），`D-02` 就需要重新验证 |
| `D-04` + `D-05` | 预判是"提前拦截"，回滚是"拦截失效后的兜底"。只有预判没有回滚，会在误判时把工作区留在合并中状态 |
| `D-09` + `D-10` + `D-11` | 三者是同一次修正的三个组成部分，单独改任何一个都会打破语义 |
