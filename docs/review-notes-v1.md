## A 级：文档自相矛盾或承诺过强

### A1 推送写入 upstream，与非目标「不改仓库 `.git/config`」冲突

**位置**
- `decisions.md:48`（`D-12` 理由栏）
- `requirements.md:149`（§6 非目标表最后一行）

**现状**

`D-12` 的理由栏以 `git push -u` 论证「自动创建远程分支」这一行为；而 §6 非目标明确写着「不改 `~/.gitconfig`、不改仓库 `.git/config`」。
`git push -u` 等价于 `--set-upstream`，会在仓库 `.git/config` 写入 `branch.<name>.remote` 与 `branch.<name>.merge`。

**问题**

两条要求在实现时必然有一方被违反。更关键的是：本插件的设计**刻意回避 "upstream" 概念**（见 `R-01`，以及 `decisions.md:92-93` 的特别提醒）。一旦仓库里被写入了 upstream，接手者误把它当作同步依据的概率会显著上升——而这正是本项目最重要的一次修正所要防止的事。

**建议改为**（二选一，推荐 ①）

**① 推荐**：`D-12` 理由栏把 `git push -u` 改为 `git push <remote> <branch>`，并补一句说明：

> 不附带 `-u`：本插件不设置也不使用 upstream（见 `R-01`）。在远程创建分支只需 `git push <remote> <branch>`，功能上无需写入仓库配置。

**② 备选**：若确实要保留 `-u`，则 `requirements.md` §6 非目标表该行必须收窄为：

> | 修改仓库 git 配置 | 不改 `~/.gitconfig`；不改仓库 `.git/config`。**唯一例外**：用户显式推送且远程无同名分支时，随该次推送写入此分支的 upstream |

同时在 `plan.md` §7 工程保障中同步登记该例外。

**理由**

`git push origin <branch>` 与 `git push -u origin <branch>` 在「创建远程分支」这件事上行为完全一致，差别只在于是否写本地配置。而写配置带来的唯一收益（后续可省略 remote/branch 参数）在本插件中不需要——插件始终显式指定 `pushTarget`。因此选择不写配置是无损的，还顺带避免了 upstream 概念在仓库里出现。

**连带影响**

`plan.md` §4 的 `gitPush(id)` 语义描述需同步明确：推送命令始终显式指定 remote 与 branch。

### A2 `NFR-05` 的回滚承诺，在 `RK-01` 场景下不成立

**位置**
- `requirements.md:130`（`NFR-05`）
- `decisions.md:31`（`D-05` 理由栏）
- `plan.md:242`（风险登记 `RK-01`）

**现状**

`NFR-05` 写着「合并失败后**回滚到原状**」，`D-05` 把它实现为 `git merge --abort`。
`RK-01` 则登记了「自动合并与用户正在编辑文件之间存在竞争」，影响栏写的是「合并可能让文件在用户眼前变动」，并在缓解栏明确写着「已知取舍：暂不加静默期」。

**问题**

git 官方文档对 `merge --abort` 的限制是：**如果合并开始时存在未提交的改动，且这些改动在合并启动之后又被修改过，`merge --abort` 可能无法重建合并前的状态**（文档中的原话即为建议避免带着大量未提交改动执行 merge）。

而 `RK-01` 描述的正是这个场景：用户正在编辑文件。也就是说：

- `RK-01` 目前被登记为「体验取舍」，但它实际削弱的是 `NFR-05` 这条**正确性承诺**；
- 二者是同一个场景的两面，文档却把它们分放在两份文件里、按不同严重级别处理。

**建议改为**

1. `requirements.md` 的 `NFR-05` 措辞收窄为：

> | NFR-05 | 合并失败后回滚到合并前状态。若合并期间工作区被外部修改（用户编辑文件、终端侧 git 操作），回滚可能不完整；此时**如实报告残留状态并要求用户确认**，不静默继续 | 不留半完成的合并状态，且不假装回滚一定成功 |

2. `plan.md` 的 `RK-01` 调整为正确性问题：

> | **RK-01** | 自动合并与用户正在编辑文件之间存在竞争 | 合并可能让文件在用户眼前变动；且可能使 `NFR-05` 的回滚不完全 | **已知取舍升级为待评估**：暂不加静默期的决定需重新确认。可选缓解：合并前后记录工作区指纹、合并失败后校验是否真正还原，未还原则显式告警 |

3. `decisions.md` 的 `D-05` 理由栏补一句边界说明：

> 边界：`merge --abort` 能还原的前提是工作区在合并期间未被外部改动。带未提交改动执行合并时，此前提需要 `RK-01` 的缓解手段来保障。

**理由**

`NFR-05` 目前的写法是一个无限定的强承诺，而它依赖的 git 原语在 `D-03` 选定的路径（脏工作区直接 merge）上恰好是有条件成立的。文档层面的正确做法不是放弃回滚，而是**把保证的条件写明**，并让风险表如实反映它与 `NFR-05` 的耦合关系。

**连带影响**

`requirements.md` §7.2 的验收项「预判无冲突但实际冲突时，能回滚到合并前状态」需补一个前提说明，或增加一条「回滚不完整时有明确提示」的验收项。

### A3 「领先 / 落后」的计算基准未定义，与 `D-09` 的双引用语义有踩坑空间

**位置**
- `requirements.md:69`（`FR-03` 状态显示表）
- `plan.md:106`（§4 接口表 `gitStatus` 行）

**现状**

`FR-03` 写的是「领先 / 落后 | 相对**远程跟踪引用**的提交数，形如 `↑2 ↓5`」。
`D-10` 把同步来源定为 `origin/HEAD`，`D-11` 把推送目标定为 `origin/<当前分支名>`，但文档没有说明这两个计数以哪一个为基准。

**问题**

「远程跟踪引用」是一个含糊的说法，至少有两种实现读法：

- 相对 `syncSource`（`origin/HEAD`）：`↑2` 表示服务器分支比主分支多 2 个提交，`↓5` 表示主分支有 5 个提交未合入。这是符合 `D-01`/`D-09` 语义的读法。
- 相对 `@{upstream}`：这正是 `R-01` 否定的做法。若实现者按此取基准，本项目最重要的一次修正就被悄悄绕过了。

同时还有一个**信息缺口**：决定「推送是否安全」的是相对 `pushTarget` 的领先情况（远程分支是否存在、能否快进推送），而这个数目前不在界面上。

**建议改为**

1. `requirements.md` `FR-03` 表格该行明确基准：

> | 领先 / 落后 | **一律相对同步来源**计算的提交数，形如 `↑2 ↓5`。**不使用 `@{upstream}` 作为基准**（见 `D-09`、`R-01`） |

2. 同一张表增加一行，把推送安全性所需的数暴露出来：

> | 相对推送目标 | 推送目标是否存在、是否领先（能否快进推送）。**推送安全性直接依赖此值** |

3. `plan.md` §5.3 详情面板的「状态摘要」区块补上「相对推送目标（是否存在 / 可否快进）」。

**理由**

`D-09` 的全部意义就是让两个方向各自可见、各自可核对。如果界面只给出一个没有标注基准的 `↑↓`，用户还是要靠记忆判断「这个箭头是跟谁比」，那么 `D-09` 想消除的歧义只消除了一半。把基准写死、把推送目标的领先度也显式列出，才算把这条决策落实到界面上。

**连带影响**

`plan.md` §4 表格 `gitStatus(id)` 的语义描述需补两个计数的基准说明。此项对 P1 原型有直接影响——原型里就要按两个基准各显示一组状态。

### A4 设置项的单一数据源未定，两处都能存「轮询间隔」

**位置**
- `plan.md:47`（§1 模块表「设置页」行）
- `plan.md:92`（§3 存储载体）
- `plan.md:110`（§4 `getSettings` / `setSettings`）

**现状**

`plan.md` §1 写设置页的对外接口是「slot `settings.section` + 插件 Config」；§4 又列出 `getSettings()` / `setSettings()` 读写「插件配置」；而 §3 说明项目清单存在 Host 侧的 `ctx.storage`。三处并列，没有说明设置项落哪一个。

**问题**

「轮询间隔」「逐项目自动同步默认值」「自动创建远程分支开关」这三项，既可能落在插件 Config，也可能落在 `ctx.storage`。两处并存时会出现经典的双源漂移：设置页改了一处，调度器读的是另一处。

这与 `D-08` 立下的原则（单一数据源，避免两边状态漂移）是同一个错误，只是从「客户端 / Host 侧」换成了「Config / storage」。

**建议改为**

1. `plan.md` §1 模块表「设置页」行的对外接口明确为：

> `getSettings` / `setSettings`（读写**插件 Config**，为设置的唯一数据源）

2. `plan.md` §3 存储载体段落补一句：

> `ctx.storage` **仅存项目清单**（`ProjectRecord`），不存任何设置项。设置项的单一数据源是插件 Config。

3. `plan.md` §4 表格末行的语义补注：「落在插件 Config，不重复写入 `ctx.storage`」。

**理由**

`D-08` 已经确立「单一数据源」原则，这里只需要把适用范围从清单扩展到设置，成本近乎为零；若不定，P2 阶段必然出现「设置页改了、调度器没读到」这类难以排查的问题。

**连带影响**

若采用插件 Config，需注意 Config 的变更是否能在不重启的情况下被调度器感知（热生效）。若不能，应在设置页明确提示「间隔变更需重新加载生效」，或选择 `ctx.storage` 作为唯一源并放弃 Config。**这是一个需要在 P2 之前定下来的二选一。**

## B 级：缺失的关键前置条件

> B 级 4 条的共同点：触发后的失败形态都是**「安静地什么都不做」**——正是 `R-01` 特别警告过、且用户最难察觉的那一类失败。

### B1 同步来源可能不存在或已过期，解析失败不得当作「无新提交」

**位置**
- `decisions.md:46`（`D-10`）
- `plan.md:174`（§6 决策矩阵第一行）

**现状**

`D-10` 把同步来源默认设为 `origin/HEAD`。决策矩阵第一行是「无新提交 | fetch 后上游与本地一致 | 什么都不做，仅更新时间戳」。

**问题**

`refs/remotes/origin/HEAD` 这个引用**不是自动存在的**：

- 它由 `git clone` 写入。若仓库是 `git init` + `git remote add` + `git fetch` 建立的，则该引用**根本不存在**；
- 若远程的默认分支发生过改名，该引用会**停留在旧值**直至被显式刷新。

一旦它不存在或失效，`git merge origin/HEAD` 会直接报错。若实现时把这个错误笼统归入「无新提交」或「拉取失败」的模糊分支，用户看到的就是**自动同步永远不работает、且没有任何解释**——这正是 `R-01` 提醒的那种失败。

**建议改为**

1. `plan.md` §6 决策矩阵在「无新提交」**之前**插入一行：

> | 同步来源不可解析 | `git symbolic-ref refs/remotes/origin/HEAD` 失败 | 记为 `skipped` 并**明确提示「同步来源不可解析」**；不得当作「无新提交」 |

2. `decisions.md` `D-10` 理由栏补一句：

> 该引用需在**导入项目时**与**每轮同步前**各解析一次；缺失或失效时用 `git remote set-head origin --auto` 尝试修复，仍失败则如实报错。

3. `ProjectRecord.syncSource`（`plan.md` §3）补一条约定：写入解析后的实际引用；无法解析时以显式标记保存（如 `unresolved`），而不是留空字符串。

**理由**

`D-10` 选择 `origin/HEAD` 而非写死 `origin/main` 的动机正是「换仓库时自动适配」。既然出发点是不假设环境，就必须处理「环境没给出这个引用」的情形。解析失败是一次需要用户介入的事件，不是一种静默的常态。

**连带影响**

`ProjectRecord` 的数据模型需允许 `syncSource` 处于「未解析」状态；面板主行需要相应展示。

### B2 提交身份缺失会导致 `git commit` 直接失败，而文档未覆盖身份预检

**位置**
- `requirements.md:149`（§6 非目标：不改仓库 `.git/config`）
- `requirements.md` §4 `FR-05`（手动提交）
- `plan.md` §7（工程保障）

**现状**

`AGENTS.md` 的环境事实表明确记录：**全局 `user.name` / `user.email` 未设置，身份是仓库级的**。而 §6 非目标又禁止插件修改仓库 `.git/config`。

**问题**

只要那四个被管理仓库里有任意一个没配仓库级身份（新建仓库、clone 后未配置、或配置被清掉都会导致），用户第一次点「提交」就会收到 git 的失败：

```
*** Please tell me who you are.
```

这是一个**必然会遇到的普通情况**，但需求、决策、计划三份文档都完全没有提到身份预检这一环。等到 P2 才在现场第一次撞上，会连带影响「提交前文件清单」的交互设计（清单都列出来了却在最后一步失败）。

**建议改为**

1. `requirements.md` `FR-05` 表格增加一行：

> | 前置校验 | 提交前校验该仓库的 `user.name` / `user.email` 是否已配置；缺失则**中止并提示用户自行在服务器上为该仓库配置身份**，插件不代设、不写任何 git 配置 |

2. `plan.md` §4 接口表 `gitCommit(id, message)` 行的语义补注：「入口处预检提交身份，缺失即返回失败及明确原因」。

3. `plan.md` §9 风险登记新增一条：

> | **RK-09** | 被管理仓库缺少仓库级提交身份 | 提交功能在该仓库上完全不可用 | `FR-05` 前置校验 + 明确提示；**不代设身份**（`D-20` 安全边界） |

**理由**

文档把「不代管凭据、不代设配置」这条边界写得很清楚，这是对的；但边界意味着**插件必须有能力识别出「这里需要用户动手」并说清楚**，否则用户只会看到一个无法理解的失败。识别身份缺失属于「报告不可达」这一类动作（与凭据处理同构），并不越界。

**连带影响**

主面板每行的状态展示可考虑增加「未配置提交身份」标记，避免用户在详情面板里才发现。

### B3 `gitStatus` 是否发起网络请求未定义

**位置**
- `plan.md:106`（§4 接口表 `gitStatus` 行）
- `plan.md:248`（`RK-07` 大仓库 `git status` 慢）

**现状**

§4 把 `gitStatus(id)` 定义为「单仓库状态：分支、同步来源、推送目标、领先落后、脏标记」。

**问题**

「领先 / 落后」和详情面板的「待合入提交」都**依赖已经 fetch 回来的远程引用**，但文档没有说明是谁、在什么时候把远程引用更新到最新的：

- 若 `gitStatus` 自己会 fetch：那么按 `FR-07` 默认 60 秒轮询、每个项目一次网络请求，四个项目即每分钟四次；`NFR-02` 的硬超时会被频繁触发，`RK-07` 的问题也会放大到网络层面。
- 若 `gitStatus` 不 fetch：那么面板展示的「领先 / 落后」可能是**很久以前**的快照，而界面没有体现这一点，用户会误以为「↓0」是当下的真相。

**建议改为**

1. `plan.md` §4 `gitStatus(id)` 语义明确为：

> 单仓库状态，**纯本地只读、不发起任何网络请求**：基于已 fetch 的远程引用计算领先 / 落后与脏标记，并返回 `lastFetchAt`。

2. 明确 fetch 的触发路径（仅三条）：
   - 自动同步轮询（`FR-07`）；
   - 用户点击「拉取」（`FR-04`）；
   - 详情面板中用户显式点击「刷新远程状态」。

3. `requirements.md` `FR-03` 状态字段表增加一行：

> | 最后 fetch 时间 | 上次成功获取远程引用的时间。**领先 / 落后均以此为前提**，超时未刷新时应在界面上体现 |

**理由**

`NFR-02`（硬超时）与 `NFR-04`（失败隔离）解决的是「单次调用失败怎么办」，但没有回答「这个调用应不应该联网」。把 `gitStatus` 定为纯本地、把网络开销集中在少数几个明确的触发点上，既控制了频率，也让界面上的「领先 / 落后」有了可解释的时效性。

**连带影响**

详情面板的「待合入提交」同样受 `lastFetchAt` 约束，需与状态摘要一并展示时间。

- [ ] 采纳

### B4 「同一仓库串行」的保证范围被写宽了

**位置**
- `requirements.md:128`（`NFR-03`）
- `plan.md:178`（§6 决策矩阵最后一行）
- `plan.md:199`（§7 同仓库串行）

**现状**

`NFR-03` 写的是「**同一仓库串行**：同时只允许一个 git 操作」；决策矩阵最后一行「同一仓库正被手动操作 | 仓库锁被占用 | 跳过本轮」。

**问题**

插件能感知的锁，只有**它自己进程内的锁**。用户在服务器终端里敲 `git` 时：

- 终端里的 `git status`、`git log` 等只读命令**不会持有** `.git/index.lock`；
- 即使是写操作，`index.lock` 也只在极短时间内存在，插件很难恰好撞上。

所以「仓库锁被占用」这个判定条件，实际只能覆盖「操作来自本插件」的情况。文档目前的表述会让实现者以为终端侧操作也已被串行化保护，从而放松对并发后果的警惕。

**建议改为**

1. `requirements.md` `NFR-03` 收窄为：

> | NFR-03 | **同一仓库经本插件的 git 操作串行**：插件自身发起的操作之间互斥。插件**不感知**用户在服务器终端发起的 git 操作；遇 `.git/index.lock` 存在时视为忙，跳过本轮 | 避免自动同步与用户在面板上的手动操作互相踩踏 |

2. `plan.md` §6 决策矩阵最后一行判定依据改为：「插件锁被占用，或 `.git/index.lock` 存在」。

3. `plan.md` §7 工程保障「同仓库串行」一行同步该口径。

**理由**

把保证范围写准，有两重收益：一是实现者不会误以为已覆盖终端操作；二是明确了 `index.lock` 的处理策略——它是插件唯一能观察到的外部占用信号，遇到时应「跳过本轮」而不是「重试抢占」（后者会与 `NFR-03` 的「不排队、不抢占」相矛盾）。

**连带影响**

`RK-01`（用户正在编辑文件）与这一条相关：编辑文件不产生锁，插件无法察觉，因此 `RK-01` 的风险只能由 A2 建议的「工作区指纹校验」来兜底，不能指望锁机制。
